# Couchers Dev Tool

The Couchers Dev Tool is a simple app that uses the Expo development client, along with OTA (over-the-air) updates, to allow devs and non-devs to easily develop and QA the native app.

It supports:

1. Running against a live (+auto reloading) local Metro URL. This covers ~95% of dev work when developing locally.
2. Running branch previews for PR reviews, without any local setup at all.

The point is that you only need to do full builds if you're changing native module code, which is rare. Everyone else installs the Dev Tool and loads the React Native JavaScript into it.

## Getting the Dev Tool

* **iOS**: via TestFlight, ask a native dev lead to be added.
* **Android**: download the APK from [the dev tool builds page](https://develop--devtool-builds.preview.couchershq.org/).

It's a dev build, so we can't distribute it through the app stores proper. The Dev Tool coexists with the staging and production apps on the same device (it has its own bundle ID), and points at the staging frontend (web) and backend by default.

## Workflow 1: local development

Run inside `app/mobile`:

```sh
npm run start:devtool
```

Then open the Dev Tool and connect to your Metro server (same network), or scan the QR code that Metro prints. JS/TS changes hot-reload like any normal Expo development setup.

## Workflow 2: PR branch previews

Every PR gets a sticky bot comment: a "previews are building" placeholder appears within seconds of the push, and is replaced with the live previews once they're built. Point your phone camera at the QR and the branch opens in your installed Dev Tool.

This is meant for reviewing PRs and for non-devs (QA, product) to test branches.

### Native shell vs web

Remember the app is mostly a web view wrapper (see [native-ota-updates.md](native-ota-updates.md) for the three-layer anatomy). A branch preview via QR loads the branch's *native shell* (the React Native JavaScript). The *web frontend* inside the WebView is a separate axis, but for branch previews it's handled for you: the branch's Vercel web preview URL is baked into the OTA bundle, so the WebView points at the branch's web code with no extra taps. You can still manually repoint the web/API URLs via the in-app dev settings, which wins over the baked-in default.

## What needs a new native build (and what doesn't)

The Dev Tool only loads JavaScript that is compatible with the native code it was built with. This is enforced by the Expo fingerprint (again, see [native-ota-updates.md](native-ota-updates.md)): if a branch changes native dependencies, `app.config.js`, or the Expo SDK, its fingerprint won't match your installed Dev Tool and the branch preview will silently refuse to load.

When that happens, you need a fresh native Dev Tool client. CI handles this: it recomputes the fingerprint on every push to the build branch and, only when it changed, builds a new client on EAS — iOS goes to TestFlight (update from the TestFlight app), Android gets a new APK on the builds page (re-download it). Pure JS/TS changes never trigger a rebuild.

So if a branch preview won't load, the first thing to check is whether your Dev Tool is up to date.

## How it works, briefly

* The Dev Tool is an Expo dev client. Dev clients hard-disable the normal `expo-updates` API, so branches load through the dev launcher's own load path instead, via a deep link:

  ```
  couchers-devtool://expo-development-client/?url=<url-encoded manifest url>
  ```

  The URL is either a Metro server (local dev) or one of our published branch manifests (PR previews). The QR codes just encode this deep link.

* On every relevant push, CI exports the JS bundle per platform (`expo export`), wraps it in an [Expo Updates protocol v1](https://docs.expo.dev/technical-specs/expo-updates-1/) manifest, and uploads it to S3 under the commit SHA. It's served via CloudFront at `https://<sha>--ota.preview.couchershq.org/<platform>/manifest`, reusing the same preview infrastructure other previews. Per-SHA content is immutable, so it caches forever and nothing ever needs invalidating.

* There is no OTA server: the manifests are static files, generated by `app/mobile/scripts/ota-bundle.mjs` in CI. The protocol is a frozen published spec.

* The web preview wiring: CI resolves the commit's Vercel preview URL (`scripts/vercel-preview-url.mjs`) and injects it into the manifest as `otaWebBaseUrl`; `config/urls.ts` treats it as the effective default web URL.

* Branch manifests are unsigned (unlike production/staging OTA updates).

The CI jobs live in `app/.gitlab-ci.yml` (`build:mobile-ota-devtool`, `preview:mobile-ota-devtool`, `preview:pr-comment`, `build:mobile-native-devtool`).
